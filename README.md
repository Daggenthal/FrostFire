# FrostFire

Runs a website and its MariaDB in containers, and backs the whole thing up properly.

FrostFire is the third take on my server backup tool, after [Peacebringer](https://github.com/Daggenthal/Peacebringer) (Bash) and [Warshade](https://github.com/Daggenthal/Warshade) (Python). Same idea, much better execution: one static binary, everything containerized, and encrypted backups that live somewhere other than `/tmp`.

## What it runs

| Service | Image | Notes |
|---|---|---|
| `db` | MariaDB 11.8 LTS | Data in `db/`, settings in `config/mariadb/` |
| `php` | PHP 8.4 FPM | mysqli, pdo_mysql, memcached, opcache. Mail goes out through msmtp |
| `web` | nginx stable | HTTPS with Let's Encrypt, reloads itself to pick up renewed certs |
| `cache` | memcached 1.6 | Reachable from PHP as `cache:11211` |
| `certbot` | certbot | Renews certificates twice a day |

Runs on Linux (Podman or Docker) and FreeBSD (Podman with native FreeBSD images). See [FreeBSD](#freebsd) for how that side works.

## Layout

Everything lives under one root, `/srv/frostfire` by default:

```
/srv/frostfire/
├── frostfire.env   Settings and secrets (mode 600)
├── config/         Your nginx, PHP and MariaDB config. Yours to edit
├── www/            The website
├── certs/          Let's Encrypt
├── acme/           ACME challenge files
├── db/             MariaDB data (backed up as a dump, never copied raw)
└── stack/          Generated by frostfire on every `up`. Don't edit
```

## Install

```sh
go build -o frostfire ./cmd/frostfire
sudo install -m 755 frostfire /usr/local/bin/
```

FrostFire needs a container engine with compose and restic 0.17 or newer. `frostfire setup` installs whatever is missing:

- Podman and podman-compose, unless a working Podman or Docker compose is already there
- restic from your distro, or the official release (checksum verified) if the distro's is too old
- Restart-on-boot for the containers (systemd)
- HTTP and HTTPS in firewalld or ufw, if one is active

It detects the distro from `/etc/os-release`, so derivatives work too. Supported families: Debian/Ubuntu/Raspberry Pi OS, Fedora, RHEL/CentOS/Rocky/Alma, Arch, openSUSE, Alpine and FreeBSD. It's safe to run again, and `--dry-run` shows the plan without changing anything.

Podman is the default. For Docker instead, use `frostfire setup --engine docker` (not available on the RHEL family or FreeBSD).

## Quick start

```sh
sudo frostfire setup          # install prerequisites
sudo frostfire init           # creates the root and frostfire.env with generated passwords
sudoedit /srv/frostfire/frostfire.env
sudo frostfire doctor
sudo frostfire repo init      # once, creates the backup repository
sudo frostfire up
sudo frostfire certs issue    # needs DNS pointing at this server
```

Save `RESTIC_PASSWORD` in your password manager. Without it the backups can't be read.

## Backups

```sh
frostfire backup              # databases, then www, certs, config and frostfire.env
frostfire list                # every backup run
frostfire restore             # restore the latest run (asks first)
frostfire restore 20261023T090000Z --db-only
frostfire prune               # keep KEEP_DAILY / KEEP_WEEKLY / KEEP_MONTHLY
frostfire repo check          # verify the repository and read back 5% of the data
```

How it works:

- Backups go into a [restic](https://restic.net) repository: encrypted, deduplicated and incremental. Any restic backend works (SFTP, S3, B2, a local disk).
- The database is dumped with `mariadb-dump --single-transaction` and streamed straight into restic. Nothing touches the disk, and if the dump fails, the snapshot is thrown away instead of saved half-written.
- The MariaDB password never appears on a command line, so it doesn't show up in `ps`.
- A restore moves the current files into `.pre-restore/` instead of deleting them, so a bad restore can be undone.

To run it nightly, add a cron entry or systemd timer, for example:

```
30 4 * * * root /usr/local/bin/frostfire backup && /usr/local/bin/frostfire prune
```

## Moving from the old server

1. On the old server, dump only the site's databases:
   ```sh
   mariadb-dump -u root -p --single-transaction --routines --events --triggers \
     --databases mysite | gzip > mysite.sql.gz
   ```
2. Copy the site into `www/`:
   ```sh
   rsync -a old-server:/usr/share/nginx/html/ /srv/frostfire/www/
   ```
3. Load the dump and recreate the site's DB user:
   ```sh
   frostfire db load mysite.sql.gz
   frostfire db shell
   # CREATE USER 'mysite'@'%' IDENTIFIED BY '...';
   # GRANT ALL ON mysite.* TO 'mysite'@'%';
   ```
4. In the site's PHP config: The database host is now `db` and memcached is `cache`, not `localhost`.
5. Either `frostfire certs issue` once DNS points here, or copy `/etc/letsencrypt` into `certs/` first.

## FreeBSD

The same commands work on FreeBSD, and backups move between Linux and FreeBSD in both directions. Under the hood it's different:

| | Linux | FreeBSD |
|---|---|---|
| Containers | Namespaces and cgroups | Jails, via Podman |
| Images | Official upstream images (mariadb, nginx, php, ...) | Built locally from FreeBSD's own `freebsd-runtime` image plus `pkg`, matching the host's release |
| Container networking | Handled by the engine | NAT and port redirects through pf |
| Image storage | Engine default | A ZFS dataset (`<pool>/containers`), or the vfs driver without ZFS |
| Restart on boot | `podman-restart.service` (or Docker) | `podman_enable=YES` in rc.conf |
| Healthchecks | Used to order startup | Not used: frostfire waits for MariaDB itself |
| Runs as | root by default | root, always (a jail requirement) |

What `frostfire setup` does on FreeBSD, following the Handbook's Podman chapter:

- Installs `podman-suite`, `podman-compose` and `restic` by port origin, so Python flavor changes (py311, py312, ...) don't break it
- Mounts fdescfs on `/dev/fd` and adds it to `/etc/fstab`
- Creates a ZFS dataset for container storage, or switches Podman to vfs on UFS
- Writes `/etc/pf.conf` with Podman's NAT and redirect anchors if you don't have one. It blocks nothing, so SSH keeps working. **An existing pf.conf is never touched**: setup stops and prints the lines to add
- Enables and starts pf, sets `net.pf.filter_local=1`, and enables `podman_enable`

Run it inside tmux or screen if you're on SSH, since starting pf can drop the session for a moment.

Paths inside the containers are the same as on Linux (`/etc/letsencrypt`, `/srv/www`, ...), even where FreeBSD would normally use `/usr/local/etc`. That's what keeps backups portable.

## Troubleshooting

Two tools, made for figuring out what went wrong:

```sh
sudo frostfire -v up                    # verbose: every command frostfire runs, with timing and exit status
sudo frostfire diag > frostfire-diag.txt   # full report: host, engine, containers, logs, backups, pf
```

Verbose mode (`-v`, `--verbose`, or `FROSTFIRE_VERBOSE=1`) works with every command. It also logs the decisions frostfire makes: which engine, which FreeBSD image version, whether a certificate exists, and what `setup` found before planning each step.

`frostfire diag` collects everything in one report: OS and versions, which settings are set (names only, never values), the container engine's info, images and containers, the last 40 log lines of every service, the backup repository, and on FreeBSD the pf rules and anchors, fdescfs, ZFS datasets and Podman's storage driver. Every command in it has a time limit, so a stuck engine can't hang the report. Secrets are never printed in either mode, but give the report a once-over before sharing it publicly.

## Development

```sh
go test ./...
```

The end-to-end test runs a real backup and restore against a local restic repository, using a fake container engine. It's skipped if restic isn't installed.

CI also runs `ci/e2e.sh` for real on a Linux runner (Docker) on every push. The same test in a FreeBSD 15 VM (Podman) runs only when started by hand from the Actions tab, since the nested VM makes it take 45+ minutes: setup twice, init, up, check PHP can reach the database and memcached, back up, break the site and database on purpose, restore, and check both came back.
